## 1. 业务背景与目标

### 1.1 业务定位

| 维度 | 定义 |
| --- | --- |
| 商业模式 | 自营 B2C（V1），平台自持库存 |
| 履约方式 | 快递配送（实物）。**V1 无虚拟商品、无门店自提**（Q4 已收敛） |
| 收入来源 | 商品进销差价 |
| 流量阵地 | 微信小程序 |

### 1.2 V1 验证目标与成功判据

**V1 只验证一件事：用户能在小程序里独立完成一次真实付款交易，且这件事有规模效应。**

| 判据 | 标准（建议值，待业务确认） |
| --- | --- |
| 成功判据 | 上线后 30 天内：累计真实支付订单 **≥ 100 笔**，来自 **≥ 50 个不同用户**，支付成功率 ≥ 85% |
| 失败判据 | 上线 30 天支付订单 < 30 笔，且流量假设（§2）已验证投放仍然无效 → 触发项目暂停评审 |
| 红线 | 支付异常 / 超卖 / 订单状态卡死 = **0 容忍**，出现即线上事故 |

### 1.3 V1 明确不做（Non-Goals）

多店铺 / 分销分销体系 / 拼团秒杀砍价 / 会员等级与积分 / 评价晒单 / 直播带货 / PC-H5 端 / 虚拟商品。

**给架构的重要约束**：V1 不做营销，但**价格计算链路必须预留优惠项结构**（优惠项 V1 恒为空）。若不预留，V2 引入优惠券时结算、退款分摊、对账三个模块需重写。这是 v1.0 评审确认的架构性决策。

## 2. 流量假设与容量预估（架构输入）

### 2.1 流量来源假设

现有小程序主业务为壁纸工具，商城为新增业务。进店 UV 预期来源：

| 来源 | 方式 | 预估占比 |
| --- | --- | --- |
| 壁纸用户导流 | 壁纸首页金刚区 / Banner 入口 | 50% |
| 社交分享 | 商品分享卡片、订单裂变 | 30% |
| 微信搜一搜 / 扫码 | 商品码、店铺码 | 20% |

> ⚠️ 该假设是 V1 最大业务风险。若上线 2 周进店 UV 显著低于预期，优先排查导流入口，而非商城内转化。

### 2.2 容量预估（供容量规划）

| 指标 | 常态预估 | 峰值预估（分享裂变/大促，放大 20 倍） |
| --- | --- | --- |
| DAU | 500 - 2,000 | 10,000 |
| 日订单量 | 5 - 50 | ≤ 1,000 |
| 下单峰值 QPS | < 1 | ≤ 5 |
| 商品数 | 50 - 500 SKU | — |
| 日支付回调量 | ≈ 订单量 × 1.5（含重试） | — |

**容量结论（业务侧给架构的明确预期）**：V1 是**小体量、重一致性**的系统。**不需要**微服务、消息队列、分库分表、读写分离。单体服务 + 关系型数据库 + 乐观锁即可满足。架构投入应集中在**交易一致性与资金安全**（§7），而非扩展性。**请勿过度设计。**

## 3. 业务板块全景

商城业务由 **10 个板块**构成（v1.1 修正：v1.0 误写为 8 个）：

| 层 | # | 板块 | 回答的业务问题 | V1 优先级 |
| --- | --- | --- | --- | --- |
| 主链 | ① | 商品供给 | 卖什么？还剩多少？ | P0 |
| 主链 | ② | 搜索发现 | 用户怎么找到货？ | P0 |
| 主链 | ③ | 购物车结算 | 买什么、买多少？ | P0 |
| 主链 | ④ | 订单支付 | 交易如何生效、如何收钱？ | P0 |
| 主链 | ⑤ | 履约物流 | 货怎么准时送到？ | P0 |
| 主链 | ⑥ | 售后逆向 | 不满意怎么退？ | P0 |
| 主链 | ⑪ | 资金结算 | 钱怎么流、怎么对账？ | P0 |
| 支撑 | ⑦ | 用户账户 | 怎么识别用户、沉淀关系？ | P1 |
| 支撑 | ⑩ | 合规风控 | 怎么不出事、能过审？ | P0 |
| 增长 | ⑧ | 营销增长 | 怎么让更多人买？ | P2（仅预留结构） |
| 增长 | ⑨ | 运营后台 | 运营怎么自己管？ | P0 |

**关键路径**：① → ③ → ④ → ⑤ → ⑥ 为串行主链，不可并行交付。⑪ 资金结算与 ④ 强耦合（退款依赖商户号余额）。

## 4. 用户购买旅程 × 板块映射

需求侧视角，供理解全局与埋点设计：

```
看到(入口) → 进店(②①) → 找到(②) → 决定(①③) → 付钱(④) → 等货(⑤) → 收货(⑤) → 出问题(⑥⑦)
   │            │          │          │           │         │         │          │
 金刚区      首页加载    搜索无结果  SKU缺货    支付失败   无物流    自动确认   退款时效
 Banner     白屏=流失    率>15%    价格疑义    回调丢失   更新=流失  后售后窗   超承诺
```

各环节流失点即 §12 埋点的事件来源。

## 5. 核心交易主链（业务时序）

```
浏览/搜索 → 商品详情(SKU选择) → 加购 → 结算(地址/运费) → 提交订单
    → 锁库存15min → 拉起微信支付 → 支付回调确认 → 订单生效
    → 运营发货(录单号) → 物流轨迹 → 确认收货(手动/自动) → 完成
    → [异常分支] 售后申请 → 审核 → 原路退款
```

**主链上任何一环不成立，交易闭环断裂。** 以下每个环节的业务规则都是架构约束。

## 6. 订单状态机（v1.1 重构：履约流与售后流解耦）

### 6.1 设计决策（推荐方案，待架构评审确认）

v1.0 状态机无法表达"部分退款"（一笔订单多 SKU，退一件是必然场景）。v1.1 采用**订单与售后解耦**：

- **订单（Order）** 只管理履约流，状态少而稳定
- **售后单（Aftersale）** 独立实体，挂在订单明细行上，管理退款流
- 复杂度控制：**每个订单同时只允许一笔"进行中"的售后单**，一笔售后单可包含一个或多个明细行（即支持整单退或部分退）

### 6.2 订单状态机（履约流）

| 当前状态 | 触发事件 | 目标状态 | 备注 |
| --- | --- | --- | --- |
| 待付款 | 支付成功确认（服务端） | 已支付 | 唯一生效依据=支付机构回执 |
| 待付款 | 用户取消 | 已取消 | 终态 |
| 待付款 | 15 分钟超时 | 已取消 | 自动触发，释放锁定库存 |
| 已支付 | 运营发货 | 已发货 | 履约起点 |
| 已发货 | 用户确认收货 | 已完成 | 终态 |
| 已发货 | 发货后 N 天超时（建议 10 天） | 已完成 | 自动确认收货 |
| 已取消 | （收到支付成功确认） | **不复活订单** | 走自动退款，见 §7.3 |

- 终态：`已完成`、`已取消`，不可逆
- **非法状态流转请求，服务端必须拒绝**（不允许前端状态驱动）

### 6.3 售后单状态机（退款流）

| 当前状态 | 触发事件 | 目标状态 |
| --- | --- | --- |
| （无） | 用户按明细行发起申请 | 待审核 |
| 待审核 | 运营审核通过 | 待退款 |
| 待审核 | 驳回（填理由） | 已驳回（终态） |
| 待退款 | 退款原路退回成功 | 已退款（终态） |
| 待退款 | 退款失败（余额不足等） | 待退款（重试 + 人工介入告警） |

**售后单准入规则**：
- 明细行未参与过任何售后单，且订单状态 ∈ {已支付, 已发货, 已完成}
- 已完成的订单：确认收货后售后窗口开放 **7 天**（建议值），窗口关闭后仅客服人工特批
- 自动确认收货与手动确认收货**效力相同**（v1.1 补充，消除 v1.0 歧义）

**库存回补规则**：仅退款（未发货）→ 不回补；退货退款且实物验收入库 → 回补。

### 6.4 退款金额口径

- 基准 = **实付金额**（非商品原价），按售后单所选明细行的实付分摊计算
- 运费：**整单退款退运费，部分退款不退运费**（建议值，待业务确认）
- 优惠分摊结构预留（V1 优惠恒为空，但金额构成字段必须支持）

## 7. 关键业务规则与一致性要求（架构约束 ★核心）

以下是 v1.0 评审确认的硬规则，**直接决定架构方案**：

### 7.1 金额一致性

1. 所有金额（商品价、运费、合计、实付）**服务端计算**，前端传值仅作展示，不参与任何计算与校验依据。
2. 订单生成后金额**不可修改**，只能取消重建。
3. 订单冻结"快照"：商品标题/图/规格/单价/地址在订单生成时固化，商品后续改价改名不影响历史订单。

### 7.2 库存一致性

1. 库存三态：可售 / 锁定（待付款 15 分钟）/ 失效。
2. 扣减模型：**下单即锁定，支付转实扣，超时自动释放**。
3. 并发要求：扣减必须原子完成（条件更新：`可售库存 >= 请求数量` 才成功），**禁止超卖后补偿**——超卖 = 0 容忍红线。
4. 售罄 ≠ 下架：售罄商品保留展示不可下单；下架商品从公开入口移除。

### 7.3 支付回调与竞态（v1.1 新增硬规则）

1. **支付成功的唯一依据是支付机构的交易确认回执**，不信任任何前端上报。
2. 回调必须**幂等**：同一笔支付通知重复到达，只生效一次（微信会重试通知）。
3. **订单取消后收到支付成功确认（用户在截止时刻拉起支付、回调延迟到达）**：
   - 不复活订单
   - 系统**自动发起全额原路退款**
   - 推送用户通知说明原因
4. 锁库存的 15 分钟与支付截止的 15 分钟必须是**同一时钟**，禁止库存已释放但订单仍可支付的窗口。
5. 支付成功但回执延迟时，订单状态查询接口必须能自动对齐（前端轮询可见正确状态）。

### 7.4 幂等性清单

| 操作 | 幂等要求 |
| --- | --- |
| 提交订单 | 同一结算会话重复提交 → 同一订单，不产生多笔 |
| 支付回调 | 同一支付单重复通知 → 只生效一次 |
| 发货 | 同一订单重复发货请求 → 只生效一次 |
| 退款回调 | 同一退款单重复通知 → 只生效一次 |

### 7.5 安全与合规约束

1. 手机号：服务端解密、加密存储，前端仅见脱敏值（`138****8000`）；明文不落小程序端。
2. 鉴权：服务端签发 token，失效自动续期；续期失败才跳登录。
3. 授权最小化：拒绝授权不阻断浏览；手机号仅在下单前强制索要（履约必需）。
4. 账户注销（v1.1 新增，个保法要求）：用户可发起注销；注销后身份信息脱敏留存（交易凭证保存义务），收货地址与手机号删除；不影响已完成订单凭证效力。
5. 隐私政策：首次进入展示并取得同意后，方可调用授权类接口。

## 8. 资金与结算（v1.1 新增板块 ⑪）

| 项 | 规则 |
| --- | --- |
| 收款主体 | 对公微信支付商户号（资质前提，见 §13 Q1） |
| 结算周期 | 微信支付默认 T+1 结算至商户号 |
| 退款资金来源 | 商户号余额；**余额不足时退款失败** → 售后单停在"待退款"并告警人工介入 |
| 对账机制 | 每日三方核对：支付流水 ↔ 订单状态 ↔ 退款记录；差异生成对账异常清单 |
| 降级方案（无支付资质时） | 仅限内部流程验证：≤ 2 周、≤ 10 单、通过对公转账/线下收款并留凭证，**禁止对外推广**（个人收款码经营性收款违反微信商户规则且涉税务风险）。长期方案必须回退到"先做商品展示、无在线交易"，不允许长期跑降级 |
| 财务权限 | 发货权限与退款权限分离，避免单人可发货又可退款 |

## 9. 概念数据模型（实体关系，非 DDL）

架构侧据此设计物理模型，字段级定义由技术方案输出：

```
用户 User 1─n 收货地址 Address
用户 User 1─n 订单 Order
用户 User 1─n 购物车项 CartItem ─→ SKU
商品 SPU 1─n SKU（规格组合唯一，至少一个，价格>0，库存≥0）
商品 SPU n─1 类目 Category（≤2 级）
订单 Order 1─n 订单明细 OrderItem（含商品/SKU/价格/规格快照 + 收货地址快照）
订单明细 OrderItem 1─n 售后单明细 AftersaleItem
售后单 Aftersale n─1 订单 Order（每订单同时仅一笔进行中售后单）
订单 Order 1─1 支付单 Payment（含回调凭据与幂等键）
SKU 1─n 库存流水 StockLog（锁定/实扣/释放/回补，可追溯）
订单 Order 1─n 状态变更记录 OrderStatusLog（操作留痕，纠纷追溯）
```

**设计要点**：
1. 订单冗余快照（明细快照 + 地址快照）是**必做项**。
2. 库存流水与状态变更记录必须落库——对账与纠纷仲裁都依赖它们。
3. 金额字段一律整数分存储，禁止浮点。
4. 优惠项结构预留：订单金额构成 = 商品小计 + 运费 - 优惠合计（V1 优惠合计恒为 0，但字段与计算链路必须存在）。

## 10. 外部依赖与集成点

| 依赖 | 用途 | 关键约束 |
| --- | --- | --- |
| 微信登录 code2session | 换取 openid 建立会话 | 服务端调用 |
| 微信支付 v3 JSAPI | 统一下单 / 支付回调 / 退款 / 对账单下载 | 回调必须 HTTPS；证书与密钥管理是安全重点 |
| 订阅消息 | 发货通知、退款结果、自动确认收货提醒 | 授权一次只能发一条；**下单成功时请求授权**（时机需产品确认） |
| 物流轨迹查询 | 快递单号轨迹展示 | 第三方 API（快递100/快递鸟）；**必须设计降级**：API 不可用时展示单号 + 人工客服入口 |
| 对象存储 + CDN | 商品图片 | 外链域名需配小程序白名单；需防盗链 |
| 内容安全检测 | 商品图/文本审核 | 小程序电商类目审核要求 |
| 客服 | 售前售后咨询落点 | 小程序审核阻塞项：入口必须存在（方案待定，Q11） |

**集成边界（架构红线）**：
- 小程序端只做展示与交互；金额、库存、订单状态、价格计算**全部以服务端为准**
- 管理后台是独立 Web 应用，不进小程序
- 所有第三方调用（支付/物流/短信）只在服务端发生，密钥不落前端

## 11. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 首屏可交互 P75 ≤ 1.5s；核心接口 P95 ≤ 500ms；商品列表分页加载（禁止全量） |
| 可用性 | 支付回调容忍机构重试（≥ 4 次）；核心链路故障有兜底文案与重试入口，禁止白屏/空白页 |
| 主包体积 | 商城模块独立分包（主包 ≤ 2MB 限制）；静态资源走 CDN |
| 审核合规 | 隐私政策、内容安全检测、客服入口、账户注销——四项均为小程序过审必需，M4 前完成 |
| 可追溯 | 关键操作（发货/改价/退款/库存调整）全部留痕：操作人 + 时间 + 前后值 |
| 埋点 | 事件：入口曝光 / 详情曝光 / 加购 / 搜索 / 提交订单 / 拉起支付 / 支付回调 / 售后申请；维度：用户、时间、页面、商品、金额 |

## 12. 指标体系（含口径定义）

**北极星：支付成功订单数 / 日。**

### GMV 三层口径（v1.1 修订）

```
应付 GMV = Σ 提交订单金额          （下单口径，诊断转化）
实收 GMV = Σ 支付成功金额          （交易口径，诊断支付链路）
净 GMV   = 实收 GMV - 退款金额     （经营口径，老板看的数字）
```

诊断链路：`进店 UV × 详情转化 × 加购转化 × 提交转化 × 支付成功率 × (1 - 退款率)`

| 指标 | 目标 | 口径说明 |
| --- | --- | --- |
| 详情 → 加购率 | ≥ 20%* | 加购 UV / 详情 UV |
| 加购 → 提交订单率 | ≥ 40%* | 提交 UV / 加购 UV |
| 提交 → 支付成功率 | ≥ 85%* | 支付成功 / 拉起支付 |
| 超时发货率 | ≤ 2% | 超过承诺发货时长订单占比 |
| 退款率 | ≤ 5% | 退款订单 / 支付成功订单 |
| 搜索无结果率 | ≤ 15% | 空结果搜索 / 总搜索 |
| 资损红线 | = 0 | 支付异常/超卖/订单卡死 |

> \* 目标值为小程序电商行业经验假设，**上线 2 周后必须用真实基线校准**（v1.1 补充声明）。
