## 总评

v1.1 的业务侧问题已基本收敛：状态机解耦、幂等清单、金额分存储、快照、容量结论（勿过度设计）都是**可以直接落进技术方案**的好输入。剩下的坑全部集中在「PRD 写了规则、但没回答怎么落地」的缝隙里——这类缝隙在支付与库存场景里就是资损。

---

## 🔴 硬伤（不补不能开工）

### T1. "已发货订单按明细行部分退款"与整单物流冲突

**位置**：§6.3 售后准入规则

准入写的是"订单状态 ∈ {已支付, 已发货, 已完成} 均可按明细行发起售后"。但**物流是整单维度**——一个订单一个包裹一个单号：

- 已发货 + 部分明细"仅退款"：钱退了，货却已经发出且包含未退商品，商家净损失
- 已发货 + 部分明细"退货退款"：用户无法只把其中一件寄回（包裹拆不开），退货单号与订单对不上

**修订建议**：售后准入按订单状态拆开——

| 订单状态 | 售后粒度 | 售后类型 |
| --- | --- | --- |
| 已支付（未发货） | **支持明细行级** | 仅退款 |
| 已发货 / 已完成 | **仅整单** | 仅退款 或 退货退款 |

整单售后时退款金额 = 实付金额（含按比例分摊），实现复杂度反而下降。此规则同时决定售后单表结构（是否需要 aftersale_item 关联明细），**必须在 M4 前定死**。

### T2. "商城独立分包"与 tabBar 硬冲突

**位置**：§11 主包体积 vs 用户既定的目录管理方式

微信小程序**原生 tabBar 页面必须在主包**，分包页面不能注册进 tabBar。而文档 §11 要求"商城模块独立分包"，若购物车/我的要进 tabBar，`pages/mall/*` 整体分包就无法成立。

**修订建议**（三选一，M1 动工前定）：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（推荐） | tabBar 页（商城首页/购物车）留主包，其余（详情/订单/地址/物流）放 `subPackages` root=`pages/mall/sub` | 目录两级，需一开始就规划 |
| B | 自定义 tabBar 组件（非原生），全部商城页面进分包 | 自制 tabbar 状态管理，工作量 +2~3 天 |
| C | 放弃分包，控制主包体积 | 商品图全走 CDN，风险是后续页面多了主包超 2MB |

无论选哪个，**商品图片一律不进本地静态资源**（§11 已写 CDN，此处强调执行）。

## 🟡 重要（M1 前定）

### T3. 三个定时任务散落各节，未形成清单

PRD 里至少有 3 个依赖"延迟触发"的规则，但只字未提实现载体：

| 任务 | 位置 | 触发时机 |
| --- | --- | --- |
| 待付款 15 分钟超时关单 + 释放锁定库存 | §6.2 / §7.2 | 下单后 15min |
| 发货后 10 天自动确认收货 | §6.2 | 发货后 10 天 |
| 确认收货后 7 天售后窗口关闭 | §6.3 | 确认收货后 7 天 |

**建议**：PRD 补一节"定时任务清单"。选云开发 → 定时触发器（最小 1 分钟粒度扫描 `payExpireAt < now` 的订单，容量预估下完全够用）；自建 → Redis ZSet 延迟队列或定时扫描。这也是 §7.3 "同一时钟" 的唯一落地方式，**归属 Q4 选型的连带决策**。

### T4. 微信支付回调的 ICP 备案前置条件缺失

**位置**：§10 支付依赖行

只写了"回调必须 HTTPS"，漏了关键前置：**自建服务器做支付回调域名必须 ICP 备案（周期 1-3 周）**；微信云开发的云函数/云托管可免备案直接接回调。这一条直接改变 Q4（云开发 vs 自建）的权衡权重，应写进 Q4 的决策输入。

### T5. 地址快照中的手机号加密口径未定

§7.5 规定手机号加密存储，§9 要求订单含地址快照。快照里的 `phone` 是否同策略加密？后台运营/财务看订单时显示明文还是脱敏？**建议**：快照手机号同样密文存储，后台展示统一脱敏，明文仅在"联系用户"动作时经权限校验后解密展示——写进 §7.5 第 1 条的补充。

### T6. P95 ≤ 500ms 的口径与云开发冷启动冲突

云函数冷启动 1-3s，首个请求必超。**建议**：指标改为"热请求 P95 ≤ 500ms，冷启动豁免"，否则 M2 验收时双方打架；若选自建后端再收紧为无条件。

## 🟢 建议（不阻塞）

1. **决策清单补两项**（§13）：Q14 订单号生成规则（建议：日期+业务前缀+序列，可读且利于对账检索）；Q15 提交订单的幂等键设计（前端生成的结算会话 ID vs 服务端签发）——这两个都是架构师 M2 必须回答的问题，现在就该挂上。
2. **对账降级**（§8）：无支付资质期间下载不了微信对账单，M2 阶段先做"订单状态 ↔ 支付回调记录"两方核对，资质到位后升级三方核对——建议在 §8 加一句，避免 M3 排期时才发现对不了账。
3. **值得肯定、可直接落地的部分**：§7 一致性规则（金额服务端计价、条件扣库存、回调幂等、取消后到账自动退款）、§9 概念模型（快照必做、库存流水可追溯、金额分存储）、§2 容量结论（单体+乐观锁，勿过度设计）——这些与主流电商落地经验一致，**后续技术方案以此为准绳执行即可**。
4. **执行层建议**：后续搭建代码框架时，mock 层应按本 PRD 规则实现（服务端计价、锁定/实扣库存、快照、幂等），让 mock 成为"内存版服务端"而非假数据回显——切换真实接口时只换传输层，业务逻辑零改动。
