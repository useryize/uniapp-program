## 一、业务定位

先把"这门生意"说清楚，再谈功能。

| 维度 | 定义 |
| --- | --- |
| 商业模式 | 自营 B2C（V1），平台自采或自持库存 |
| 供给来源 | 自有商品 / 精选 SKU |
| 履约方式 | 快递配送（实物） |
| 收入来源 | 商品进销差价 |
| 流量阵地 | 微信小程序（社交分享 + 搜一搜 + 订阅消息） |
| 目标用户 | 已被小程序触达、愿意在此完成完整购买闭环的用户 |

### V1 的业务取舍

**一句话**：V1 只证明一件事——**用户能在小程序里独立完成一次真实付款交易**。

为此我们主动放弃：多店铺、分销、拼团、秒杀、会员等级、积分、评价体系、直播。
这些能力在交易闭环未跑通前投入，只会分散资源并抬高数据模型复杂度。

## 二、业务板块全景

商城业务由 **8 个板块**构成，分为三层：主链、支撑、增长。

```
【主链】  ① 商品供给 → ③ 购物车结算 → ④ 订单支付 → ⑤ 履约物流 → ⑥ 售后逆向
【支撑】  ② 搜索发现        ⑦ 用户账户        ⑩ 合规风控
【增长】  ⑧ 营销增长        ⑨ 商家运营后台
```

| # | 板块 | 回答的业务问题 | V1 优先级 |
| --- | --- | --- | --- |
| ① | 商品供给 | 我们卖什么？还剩多少？ | **P0** |
| ② | 搜索发现 | 用户怎么找到想要的货？ | **P0** |
| ③ | 购物车结算 | 用户决定买什么、买多少？ | **P0** |
| ④ | 订单支付 | 交易如何生效？如何收钱？ | **P0** |
| ⑤ | 履约物流 | 货怎么准时送到？ | **P0** |
| ⑥ | 售后逆向 | 不满意了怎么退？ | **P0** |
| ⑦ | 用户账户 | 怎么识别用户、沉淀关系？ | P1 |
| ⑧ | 营销增长 | 怎么让更多人买、买得更勤？ | P2 |
| ⑨ | 商家运营后台 | 怎么让运营自己管得动？ | **P0** |
| ⑩ | 合规风控 | 怎么不出事、能过审？ | **P0** |

### ① 商品供给

**板块目标**：把"卖什么、多少钱、还剩多少"定义清楚，且保证前台展示与实际可售**始终一致**。

**核心业务对象**
- 类目（≤ 2 级）
- 商品（SPU）：一件可售商品，如"T恤"
- 单品规格（SKU）：最小可售单位，如"T恤-白色-M码"
- 价格
- 库存

**关键业务流程**

商品建档 → 归属类目 → 定义 SKU 与价格 → 录入库存 → 上架

**核心业务规则**

1. 一个商品**至少一个 SKU**，SKU 组合不可重复。
2. **价格永远只有一个生效售价**（V1 不做多价格体系）；划线价仅作展示，不可下单。
3. 库存有三态：
   - **可售** —— 正常可下单
   - **锁定** —— 用户已下单待付款，锁定 15 分钟
   - **失效** —— 售罄或被下架
4. **售罄 ≠ 下架**：
   - 售罄商品**保留展示**（用户可浏览、可收藏），但不可下单
   - 下架商品**从公开入口移除**，仅历史订单链接可达
5. 上架前校验：至少一个 SKU 有库存、售价 > 0、类目合法、详情完整。**校验不通过不允许上架**。
6. 商品改价、改名、下架**不影响历史订单**——历史订单永远展示购买当时的信息。
7. V1 不做商品评价与虚拟商品。

**主要角色**：运营

---

### ② 搜索发现

**板块目标**：用户能主动找到目标商品，而不是被动等推荐。

**核心业务对象**：搜索行为、商品列表、筛选条件

**关键业务流程**

进入商城 → 浏览推荐位 **或** 主动搜索 → 筛选/排序 → 进入详情

**核心业务规则**

1. 排序维度固定为四项：综合、销量、价格升降、上新。
2. 筛选维度 V1 仅两个：价格区间、分类（层级≤2，无需级联筛选）。
3. **搜索无结果率是核心健康指标**，超过 15% 说明供给或搜索有问题。
4. 搜索历史仅存本地，上限 10 条，可一键清空。
5. 售罄商品在列表中默认**过滤**（不占位），但在搜索结果中可展示为置灰态。

**主要角色**：用户、运营（通过补充关键词与标题优化）

---

### ③ 购物车与结算

**板块目标**：把"想看"转化为"想买"，并锁定交易意愿。

**核心业务对象**：购物车条目、结算会话

**关键业务流程**

加购 → 勾选/改量 → 进入结算 → 确认信息 → 提交订单

**核心业务规则**

1. **加购即校验**：可售状态、库存上限，校验不通过不允许加购。
2. **价格变动告知**：结算时价格与加购时不一致，必须显式提示用户确认后才能继续（知情权是硬要求）。
3. 运费规则 V1 只支持一条：满额免运费，未满收取固定运费。（门槛与金额需业务定）
4. 一次结算**生成一个订单**（单商家，无需拆单）。
5. **提交订单即锁定库存 15 分钟**，这是库存与订单之间的契约边界。

**主要角色**：用户

---

### ④ 订单与支付

**板块目标**：把购买意愿变成有法律效力的交易，并完成收款。

**核心业务对象**：订单、支付单

**关键业务流程**

创建订单 → 拉起支付 → 支付确认 → 订单生效（触发履约）

**核心业务规则**

1. **订单状态机是业务核心契约**，任何"已支付又取消""已发货又退款"的组合都必须被业务规则明确禁止或明确允许：

| 当前状态 | 允许动作 | 结果 |
| --- | --- | --- |
| 待付款 | 取消 / 支付成功 | 已取消 / 已支付 |
| 已支付 | 申请退款 / 发货 | 退款中 / 已发货 |
| 已发货 | 确认收货 / 申请退款 | 已完成 / 退款中 |
| 退款中 | 审核通过 / 驳回 | 已退款 / 已发货（驳回） |
| 已取消 / 已完成 | — | **终态，不可逆** |

2. **支付成功的唯一依据是支付机构的交易确认，不信任前端上报**。
3. 订单创建后 **15 分钟未支付自动取消**，库存自动释放。
4. **金额一经生成不可修改**，只能取消后重新下单。
5. **支付成功即产生发货义务**——这是履约的起点，也是售后倒计时的起点。
6. 幂等要求（业务表述）：同一提交动作不产生两笔订单；同一笔支付的重复确认不产生多次生效。

**降级方案（无支付资质时）**
用户提交订单 → 状态"待商家确认" → 运营在后台人工确认收款 → 转入已支付。
此模式下用户无法自助支付，转化率预期显著下降，仅用于资质未到位时的过渡验证。

**主要角色**：用户、支付机构、运营

---

### ⑤ 履约与物流

**板块目标**：把货**准时、准确**送到用户手上。

**核心业务对象**：发货单、物流轨迹、签收事件

**关键业务流程**

已支付 → 运营备货打单 → 录入物流单号 → 用户查看物流 → 签收

**核心业务规则**

1. **仅已支付订单可发货**，这是履约的准入门槛。
2. 发货后**必须推送用户通知**（订阅消息），否则用户无从知晓。
3. **地址修改规则**：发货前用户可自助改地址；发货后不可自助修改，需走客服/售后渠道。
4. 签收有两种：用户主动确认收货 / 超时系统自动确认收货。
   - **自动确认收货时限需业务确定**（如发货后 10 天），期限过短会损害用户权益，过长会拖慢结算与售后窗口。
5. 物流异常（长时间无轨迹更新）必须有兜底：展示单号 + 人工客服入口，不允许出现空白页。

**主要角色**：运营（发货）、承运商、用户

---

### ⑥ 售后与逆向

**板块目标**：处理交易后的不满，把投诉转化为可控成本而非平台信誉损失。

**核心业务对象**：售后单、退款单

**关键业务流程**

用户发起申请 → 运营审核 → 处置（仅退款 / 退货退款 / 驳回）→ 资金原路退回

**核心业务规则**

1. **售后入口按订单状态开放**：
   - 已支付未发货 → 仅支持**仅退款**
   - 已发货未签收 → 支持**仅退款 / 退货退款**
   - 已完成 → 按售后时效政策处理
2. **库存回补规则**（极易出错，明确区分）：
   - 仅退款 → **不回补库存**（货已发出或未发出但不再回流）
   - 退货退款且实物入库 → **回补库存**
3. **退款金额口径**：
   - 基准是**实付金额**，不是商品原价
   - 运费是否退还需业务定（建议：整单退款退运费，部分退款不退运费）
4. **时效承诺**：用户提交申请后，运营需在承诺时长内处理（建议 48 小时），超时自动升级。
5. 常见责任场景的归属规则（需业务定）：
   - 商家缺货导致无法发货 → 全额退款 + 是否补偿运费
   - 超时未发货 → 用户可无条件取消并退款
   - 错发/漏发/破损 → 用户举证后由商家承担退货运费
6. **恶意退款风控**：短期内高频申请仅退款的账号需进入人工审核名单。

**主要角色**：用户、运营、客服

---

### ⑦ 用户账户

**板块目标**：识别用户、沉淀关系，让用户从"一次性访客"变成"可触达的资产"。

**核心业务对象**：用户身份、收货地址、收藏、浏览行为

**核心业务规则**

1. **手机号是履约的必需品**（发货联系），因此下单前强制绑定；但**浏览阶段绝不强制索要**。
2. **最小必要授权**：拒绝授权不得阻断浏览，仅在加购/下单时二次引导。
3. 收货地址：支持新增/编辑/删除/设为默认，支持从微信地址一键导入。
4. 收藏与浏览记录跨设备同步。
5. **用户分层 V1 只做标签，不做等级**：记录是否购买过、累计订单数、累计金额、最近购买时间。会员等级与权益体系属于 P2。
6. 用户数据采集遵守个人信息保护要求，敏感信息脱敏展示。

**主要角色**：用户

---

### ⑧ 营销与增长

**板块目标**：提升转化率与复购率。**V1 全部不做，但必须预留数据结构。**

**核心业务规则（关键决策）**

> ⚠️ **即使 V1 不做营销，订单的价格计算链路与金额构成必须从第一天起就按"可容纳优惠项"设计。**

理由：优惠不是一个字段，而是贯穿「商品标价 → 优惠计算 → 实付金额 → 退款分摊」的整条链路。V2 加营销时若链路未预留，需要重写结算、退款、财务对账三个模块，代价远高于现在多设计一步。

**为 V2 预留的能力**
- 优惠项（券/满减/活动）可挂载在订单上，V1 恒为空
- 商品可配置活动价，V1 不启用
- 分享与拼团等社交玩法预留入口位

**V2 规划**：优惠券、限时秒杀、拼团、分销返佣、会员等级、积分、评价晒单、订阅消息精细化触达。

**主要角色**：用户、运营

---

### ⑨ 商家运营后台

**板块目标**：让运营**不依赖开发**就能完成日常交易与履约。

| 后台模块 | 核心业务能力 | 优先级 |
| --- | --- | --- |
| 商品运营 | 上架/下架、类目与 SKU 维护、库存调整、价格维护 | P0 |
| 订单履约 | 订单查询、发货（录入物流）、改地址、改单 | P0 |
| 售后处理 | 退款审核/驳回、触发原路退款与库存回补 | P0 |
| 交易数据 | 销售额、订单量、转化漏斗、退款率 | P1 |
| 用户运营 | 用户查询、收货地址（脱敏）、黑名单 | P1 |
| 营销配置 | 优惠券、活动位、推荐位 | P2 |

**核心业务规则**

1. 后台**不在小程序内**，是独立的管理界面，仅管理员可访问。
2. **关键操作必须留痕**：发货、改价、退款、库存调整均记录操作人与时间，以应对纠纷与对账。
3. 权限最小化：发货与退款是两个权限，避免单人可发货又可退款造成的资损风险。

**主要角色**：运营、店长、财务

---

### ⑩ 合规与风控

**板块目标**：不出事、能过审。

**必备资质与材料**

| 项 | 是否阻塞上线 |
| --- | --- |
| 营业执照 / 个体工商户主体 | **是** |
| 微信支付商户资质 | **是**（无则走降级方案） |
| 行业类目资质（如食品经营、出版物许可） | 视类目而定 |
| 隐私政策文本 | **是**（小程序审核必需） |
| 客服联系方式 | **是** |

**核心业务规则**

1. **隐私合规**：首次进入展示隐私政策，用户同意后才调用需授权的能力。
2. **支付安全**：不信任前端金额与状态；支付确认以机构回执为准。
3. **退款风控**：防止"仅退款套利"，异常账号人工审核。
4. **客服承接**：售前咨询、售后投诉、发货异常三个入口必须有明确落点，不能是"请联系客服"这种空指引。

**主要角色**：法务、运营、平台

## 三、板块之间的业务依赖

| 上游 | 下游 | 依赖内容 |
| --- | --- | --- |
| ① 商品供给 | ② 搜索发现 | 无可售商品则搜索无意义 |
| ① 商品供给 | ③ 购物车结算 | 无 SKU 与库存则无法加购 |
| ③ 购物车结算 | ④ 订单支付 | 结算金额即为订单金额基准 |
| ④ 订单支付 | ⑤ 履约物流 | **支付成功是发货的唯一准入条件** |
| ⑤ 履约物流 | ⑥ 售后逆向 | 签收时点决定售后窗口开启时点 |
| ④ 订单支付 | ⑥ 售后逆向 | 实付金额决定退款上限 |
| ⑩ 合规风控 | 全部 | 支付资质与隐私合规阻塞上线 |
| ⑨ 运营后台 | ①④⑤⑥ | 后台是这些板块的操作入口 |

**关键路径**：① → ③ → ④ → ⑤ → ⑥ 是一条不可并行的串行主链。任何一段不通，交易即无法完成闭环。

## 四、业务指标体系

### 北极星指标

**支付成功订单数 / 日** —— 唯一同时反映流量、转化与交易健康的指标。

### GMV 拆解（用于诊断问题出在哪一段）

```
GMV = 进店 UV × 下单转化率 × 支付成功率 × 客单价
```

任一环节异常都能定位到具体板块，这是排障的第一诊断路径。

### 分层指标

| 层次 | 指标 | 说明 | 目标 |
| --- | --- | --- | --- |
| 流量 | 进店 UV | 板块② 入口效率 | — |
| 转化 | 商品详情 → 加购率 | ① 提供吸引力 | ≥ 20% |
| 转化 | 加购 → 提交订单率 | ③ 结算摩擦 | ≥ 40% |
| 转化 | 提交 → 支付成功率 | ④ 支付链路健康度 | ≥ 85% |
| 交易 | 支付成功订单数/日 | 北极星 | — |
| 交易 | 客单价 | ① 价格策略 | — |
| 履约 | 超时发货率 | ⑤ 运营能力 | ≤ 2% |
| 售后 | 退款申请率 | ⑥ 商品质量信号 | ≤ 5% |
| 健康 | 搜索无结果率 | ② 供给覆盖度 | ≤ 15% |
| 红线 | 支付异常 / 超卖 / 订单卡死 | 资损 | **= 0** |

### 诊断逻辑

- 进店 UV 低 → 问题在流量入口，不在商城
- 详情→加购率低 → 问题在① 商品（价格/详情页说服力）
- 加购→提交低 → 问题在③ 结算（运费/地址摩擦）
- 提交→支付低 → 问题在④ 支付（链路报错/信任不足）
- 退款率高 → 问题在① 商品质量或⑤ 发货时效

## 五、待业务方决策事项

## 六、分期建议（按业务板块切）

| 阶段 | 交付板块 | 业务里程碑 |
| --- | --- | --- |
| **M1 看得见** | ①② + 后台商品运营 | 用户能浏览、能搜索，运营能上架 |
| **M2 买得成** | ③④ + 后台订单履约 | **能收到第一笔真实付款** ← 核心验证点 |
| **M3 交得出** | ⑤ + 地址管理 | 能真实发货、用户能查物流 |
| **M4 退得掉** | ⑥⑩ + 合规材料 | **可提交小程序审核上线** |
| **M5 留得住** | ⑦⑧ + 数据看板 | 沉淀用户资产，具备增长基础 |

**里程碑判断**：M2 完成 = 商业模式验证成立；M4 完成 = 可公开上线；M5 完成后才具备投放与规模化运营条件。

## 七、业务风险登记

| 风险 | 业务后果 | 应对 |
| --- | --- | --- |
| 无支付资质 | 无法上线真实交易，模式不可验证 | Q1 优先决策 |
| 履约跟不上 | 用户付款后不发货，投诉与信誉损失 | M2 前先确认发货产能 |
| 超卖/订单卡死 | 直接资损 | 库存与订单规则纳入验收清单 |
| 审核驳回 | 上线延期 | 隐私政策与资质 M2 前备齐 |
| V1 加营销 | 结算/退款/对账三模块重写 | 价格链路预留优惠项结构 |
| 售后无承接 | 投诉升级为平台处罚 | 客服落点在 M4 前确定 |
